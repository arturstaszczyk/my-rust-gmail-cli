1Context

Problem

The claude.ai Gmail connector can't download attachments. The third-party gmail-cli (Bun/TS) works, but isn't trusted and needs Bun.

Goal

Our own single static-ish Rust binary on the Gmail REST API, agent-first with readable human output.

First concrete use case: find an email, save its PDF, let the agent read it

Step 1
mg search
Find the thread by Gmail query
→
Step 2
mg attachment save
Write PDF to --out dir, print path only
→
Step 3
Claude reads the PDF
With its Read tool, from disk

2Decisions made

Scope

Gmail read + attachments, organize, drafts/send. No Calendar/Drive.

Output

Agent-first: compact JSON when piped, text in a TTY.

Token storage

OS keyring (Secret Service).

Sending

Agents create drafts only. Sending needs a human at a TTY.

OAuth app

"In production", unverified. Refresh token doesn't expire after 7 days.

Accounts

Single account.

Toolchain

Rust via mise.

Distribution

Local build only. No CI or releases.

7The send gate

Agents can only create drafts. Sending is a separate step that needs a real person at a real terminal.

Agent
mg reply <id> --body …
Creates a draft, prints draft id
→
Anyone
mg draft send <id>
confirm.rs opens /dev/tty
→
No TTY (agent, pipe)
Refused
Exits with an error, nothing sent
Real TTY
Preview → type send → sent
Anything else aborts
$ mg draft send r-4821 To: kazimierz@example.pl Subject: Re: Naliczenie --- Dziękuję, potwierdzam odbiór... Type "send" to send this draft: send Sent. $ mg draft send r-4821 | cat {"error":"no TTY: draft send requires a human at a terminal","hint":"run it yourself in a terminal"}

Illustrative output; exact wording is decided at M3.

9Security design

Scope: gmail.modify

Reachable

Read, labels, trash, drafts, send.

Unreachable by design

Permanent delete, settings (filters, forwarding).

Where secrets live

SecretStored inLifetime
Refresh tokenOS keyring onlyLong-lived (production app)
Access tokenMemory onlyOne run; refreshed each run (cheap)
Client id / secretConfig file (0600)A desktop client secret isn't really secret

OAuth login flow

1
Bind 127.0.0.1:0
Random port
→
2
Open browser
PKCE S256 challenge + random state
→
3
Single redirect
Check state, then close. 5-min timeout
→
4
Exchange code
Refresh token → keyring

Invariants

Hardcoded hosts only

gmail.googleapis.com, oauth2.googleapis.com (incl. /revoke), accounts.google.com.

Sanitized output

C0/C1 controls and ANSI/OSC escapes stripped from all text. JSON escaped by serde. Fixes the gmail-cli weakness.

Validated ids

Message, thread and attachment ids must match [A-Za-z0-9_-]+ before going into URLs.

No telemetry

No update checks. Writes only config, keyring and saved attachments.

10Weak sides (accepted or mitigated)

Accepted, notable impact Accepted, limited impact Mitigated
1

Draft-only is enforced by the CLI, not Google

gmail.modify can send. A leaked refresh token can send mail as you. No Google scope allows drafts but blocks sending.

Accepted
2

Keyring doesn't isolate apps

Any process running as you on an unlocked session can read the token. Protects against plain-file leaks, not same-user malware.

Accepted
3

Unverified production app

Warning at every login. Google could tighten the policy later.

Accepted
4

Prompt injection

Email content flows into the agent's context. The draft gate limits damage but can't stop the agent being misled while reading.

Partly mitigated
5

Single account

Other addresses unreachable. Keyring keyed by email keeps a later --account cheap.

Accepted
6

Messy real-world mail

Charsets, broken MIME, giant HTML. encoding_rs, truncation, fixture tests. Edge cases will remain.

Mitigated
7

Quotas

Per-user rate limits. Use threads.get over per-message calls; back off on 429.

Mitigated
8

Maintenance

You own it: cargo update + cargo audit now and then.

Accepted

12One-time setup (yours, about 5 minutes)

  1. Install the toolchain: mise use -g rust
  2. Google Cloud console: create a project and enable the Gmail API.
  3. OAuth consent screen: External, add the gmail.modify scope, click Publish app (move to production).
  4. Credentials: OAuth client ID, type Desktop app, download the JSON.
  5. mg auth setup --client-json ~/Downloads/client_secret_*.json, then mg auth login. Click through the "unverified app" warning once.

Install

cargo build --release
cp target/release/mg ~/.local/bin/

Uninstall

rm ~/.local/bin/mg
rm -rf ~/.config/my-google-cli
secret-tool clear service my-google-cli

Then revoke access at myaccount.google.com/permissions.
